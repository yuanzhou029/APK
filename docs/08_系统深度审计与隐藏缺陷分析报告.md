## 1. 审计综述与背景

AI-MA v5.3.0 系统成功完成了从早期的单进程 Python 纯软件循环到“**Rust 44Hz 硬实时微内核 (`aima-rt-daemon`) + Python 业务中枢 (`control_station.py`) + `/dev/shm` 零拷贝双缓冲 Seqlock 共享内存**”的高异构分布式协同演进。

本审计工作作为正式投产部署前的最后一道质量与安全关卡，立足于生产环境的**极限可靠性、实时性断流防护、物理硬件安全防御及网络防御安全**，对系统进行了跨层级、跨语言（Rust/C ABI/Python）的代码逻辑审查、机制验证与潜在失效模式（FMEA）分析。

本报告系统性归纳了当前实装代码中潜藏的 **4 项关键性设计/安全缺陷**与 **3 项深层次系统讨论议题**，并给出明确的工业级修复建议。

## 2. 核心隐藏缺陷分析与根本原因 (Root-Cause Analysis)

### 缺陷 1：跨多 Universe 宏特效的渲染截断与数据丢失 (高危 · 业务逻辑)

- **涉及源码**: `core/engine.py:202-208`
- **代码快照**:
  ```python
  fixtures = params.get("fixtures", [])
  if fixtures:
      u = fixtures[0].get("universe", 0)
      try:
          base_frame = self.dmx_merger.get_final_frame(u)
          new_frame = macro.render(elapsed_ms, params, bytearray(base_frame))
          self.dmx_merger.submit_frame("active_macro", u, new_frame, priority=PriorityLevel.AI_MACRO)
      except Exception as e_m:
          logger.error(f"动态特效宏演算发生故障，已自动保护性熔断停止: {e_m}")
          self.stop_macro()
  ```
- **机理与根本原因剖析**:
  1. 系统在调用背景动态宏（如走马灯 `macro_marquee`、呼吸灯 `macro_breathing`）时，允许参数 `params["fixtures"]` 传入包含全场多个灯具的列表。
  2. 然而，在 `_update_macro()` 的调度逻辑中，代码硬编码只提取了灯具列表中**首个元素所在的 Universe** (`fixtures[0].get("universe", 0)`)，且仅针对该 Universe 读取底帧并调用单次 `macro.render(...)`。
  3. **失效后果**: 若场地灯光配置跨越了多个 Universe（例如面光在 Universe 0，侧光/电脑摇头灯在 Universe 1 和 2），则只有 Universe 0 能收到宏演算数据，Universe 1 和 2 的灯具将完全处于静默冻结状态，造成大型演出中跨 Universe 灯具效果的严重撕裂与失效。
- **推荐修复方案**:
  在 `engine.py` 中将 `fixtures` 按 `universe` 进行字典分组聚合，循环驱动宏插件分别渲染并提交到对应的 Universe；或者重构宏接口协议，允许宏插件一次性返回各 Universe 的通道差量。

### 缺陷 2：L4 共享内存掩码“以零值为判断”导致的黑场失效与状态残留 (高危 · 实时控制)

- **涉及源码**: `core/engine.py:116-118`
- **代码快照**:
  ```python
  for u in range(self.dmx_merger.universe_count):
      frame = self.dmx_merger.get_final_frame(u)
      # 生成活跃通道掩码 (若通道值不为 0 则激活掩码)
      mask = bytearray(1 if val > 0 else 0 for val in frame)
      self.kernel_bridge.submit_layer("l4", u, frame, mask)
  ```
- **机理与根本原因剖析**:
  1. 微内核共享内存槽位（`aima_layer_shm_slot_t`）采用了“数据缓冲 + 活跃掩码（`active_mask`）”双轨控制机制。微内核仅对 `mask[ch] == 1` 的通道执行当前槽位（L4）覆盖仲裁。
  2. `engine.py` 当前错误地将“**DMX 通道数值是否大于 0** (`val > 0`)”等同于“**该通道是否需要生效控制**”。
  3. **失效后果 (严重的控制反转)**:
     - 在 DMX-512 标准中，通道电平 `0` 是极具明确控制含义的状态（例如：总调光 Dimmer 关死、暗场 Blackout、三原色 RGB 熄灭、频闪通道置为常闭关断）。
     - 当上层控制台或用户意图主动将灯具亮度调为 `0` 时，由于计算出的 `mask` 位变为 `0`，微内核会判定“L4 槽位在该通道无意图输出”，从而自动穿透退让到下层槽位（如 L3 创意层、L2 底座层），或者继续保持历史残留帧！
     - 现象即表现为：**灯具无法关死、暗场失败、残影拖尾**。
- **推荐修复方案**:
  - DmxMerger 必须维护一个显式的“脏标记掩码”（Dirty Mask）或由知识库配置的活跃通道物理白名单，明确区分“主动输出 0 电平”与“通道未占用释放”。

### 缺陷 3：3 类插件上传热重载中的路径穿越漏洞 (高危 · 网络与系统安全)

- **涉及源码**: `control_station.py:1700-1715`
- **代码快照**:
  ```python
  filename = req_data.get("filename", "plugin.py")
  if not file_b64 or not filename.endswith(".py"):
      ...
  save_dir = os.path.join(engine.plugin_host.plugins_dir, "community")
  dest_path = os.path.join(save_dir, filename)
  with open(dest_path, "wb") as f:
      f.write(file_bytes)
  ```
- **机理与根本原因剖析**:
  1. 接口 `/api/plugins/community/upload` 接收前端提交的 `filename` 参数。代码虽然校验了后缀名以 `.py` 结尾，但**未对文件名进行规范化路径清洗（Sanitization）**。
  2. 若攻击者构造恶意请求传入 `filename = "../../core/engine.py"`，`os.path.join` 会将相对路径向上解析穿越，直接跳出 `plugins/community` 目录，将核心模块覆盖为任意内容。
  3. 随后代码立即执行 `engine.plugin_host.load_plugin_from_file(...)`，直接将传入的代码动态 `import` 到主进程中，导致**任意代码执行 (RCE)** 与系统控制权沦陷。
- **推荐修复方案**:
  ```python
  safe_name = os.path.basename(filename)
  # 强制限制文件名必须为合法的 Python 标识符命名 (纯字母、数字、下划线)
  name_without_ext = os.path.splitext(safe_name)[0]
  if not name_without_ext.isidentifier() or not safe_name.endswith(".py"):
      self._send_json({"status": "error", "message": "非法插件文件名"}, 400)
      return
  dest_path = os.path.join(save_dir, safe_name)
  ```

### 缺陷 4：微内核崩溃重启后共享内存 Client 句柄失去同步 (中高危 · 高可用容灾)

- **涉及源码**: `control_station.py:364, 403` 与 `core/kernel_bridge.py`
- **机理与根本原因剖析**:
  1. 在 `control_station.py` 中，运行期看门狗 `_kernel_watchdog_loop()` 会定期巡检伴生微内核。当检测到微内核异常退出时，看门狗会调用 `ensure_microkernel_running()` 重启二进制进程。
  2. 然而，`AimaKernelBridge` 是单例模式，在系统初始化时即生成了 `_clients["l1"] ~ ["l4"]` 和 `_core_client`，其底层映射了内存文件（在 Linux 下为 `/dev/shm/*`，Windows 下为命名内存映射）。
  3. 当微内核进程崩溃退出并被系统重新拉起后，虽然内核重新打开了同名共享内存段，但 Python 侧原持有的共享内存句柄或指针可能已经指向陈旧、损坏或未重置的 Seqlock 锁状态。
  4. 当前看门狗在重启微内核后**并未通知 `AimaKernelBridge` 进行重连 (`reconnect()`)**，导致 Python 写入的依然是断开前的死锁状态，推流无法自动恢复。
- **推荐修复方案**:
  在 `AimaKernelBridge` 中实现 `reconnect()` 方法，清空并重新初始化所有 `AimaPythonShmClient` 实例；在看门狗每次成功重新拉起微内核后，显式调用 `AimaKernelBridge.get_instance().reconnect()`。

## 3. 架构深度讨论与技术演进议题 (System Discussion)

### 议题一：Universe 规模演进（4 宇宙 vs 64 宇宙不匹配问题）
- **现状矛盾**:
  - Rust 硬实时微内核（`aima-rt-daemon`）与底层 C 结构体（`aima_shm.h`）标准设计为 **64 Universes**（支持 `AIMA_MAX_UNIVERSES 64`，即 $64 \times 512 = 32768$ 控制通道）。
  - 但上层 Python `DmxMerger`（`core/dmx_merger.py`）在 `__init__` 中默认写死 `universe_count = 4`。
- **演进讨论**:
  - 4 个 Universe（2048 通道）只能满足小型 Livehouse 或剧场，无法满足大型舞台全景灯阵（动辄数十 Universe）的需求。
  - 应将 `dmx_merger.py` 的容量扩展为动态或统一配置为 64，利用 NumPy 的矢量化操作优化 Python 侧 64 宇宙的 HTP/LTP 运算性能，消除两层在容量设计上的落差。

### 议题二：物理安全钳位 LUT 的动态下发同步机制
- **现状矛盾**:
  - `aima_shm.h` 中设计了 `safety_lut[64][512][256]`，实现了 $O(1)$ 零分支安全钳位。
  - 目前在 Python 业务层，知识库场地拓扑配置发生热变更（如用户新增或修改了电脑灯的通道安全属性）时，Python 侧缺少一条将新安全规则编译并原子同步写入微内核 `safety_lut` 的通道。
- **演进讨论**:
  - 建议在 `aima_shm_sdk` 中补充向 `aima_core_state` 写入 `safety_lut` 的专用 ABI 方法；当场地切换（`/api/kb/switch_venue`）或灯库保存时，由 Python 端自动计算并一次性刷新共享内存中的 LUT 表，实现软硬件安全协同闭环。

### 议题三：Linux 生产环境特权解耦与用户隔离
- **现状矛盾**:
  - 当前实装部署中，微内核与控制台 systemd 单元均使用 `User=root` 运行（为了调用 `mlockall` 锁页、`SCHED_FIFO` 实时调度以及使用某些网络特权）。
  - 这种粗放式的 root 权限与 Web 服务混合运行，放大了 Web 漏洞（如缺陷 3 中的代码注入）对宿主机的威胁。
- **演进讨论**:
  - 采用 Linux Capabilities 进行细粒度提权：为微内核单独赋予 `CAP_SYS_NICE`、`CAP_IPC_LOCK` 与 `CAP_NET_BIND_SERVICE`，并以专用的 `aima` 独立系统用户运行；Web 控制台则完全降权运行，以达到金融/工业级安全基线。
