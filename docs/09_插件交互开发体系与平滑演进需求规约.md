## 二、 方案二：插件间的数据与功能交互方案

### 2.1 需求拆解与功能边界
* **Service Broker（服务代理）**：为三类插件（`BaseCreativePlugin` / `BasePerceptionPlugin` 等）及底层适配件提供统一的服务注册、发现与安全调用代理，防止插件间直接强引用导致耦合或内核崩溃。
* **安全 RPC**：支持插件间同步/异步远程过程调用（RPC），所有方法调用需经过白名单鉴权、参数类型及范围校验。
* **EventHub（事件总线）**：基于发布-订阅（Pub/Sub）模式的异步事件广播通道，支持解耦的跨插件事件驱动（如音频节拍触发、场景演化通知等）。
* **状态只读镜像（Read-only State Mirror）**：基于共享内存 `seqlock` / 零拷贝机制，向非特权插件安全暴露微内核实时灯光状态与遥测环的只读快照，严禁写越权。

### 2.2 接口契约与签名
* **Service Broker 注册与调用契约**：
  ```python
  class ServiceBroker:
      def register_service(self, plugin_id: str, service_name: str, handler: Callable, spec: dict) -> None: ...
      def unregister_service(self, plugin_id: str, service_name: str) -> None: ...
      def call_service(self, caller_id: str, service_name: str, payload: dict, timeout_ms: int = 500) -> Any: ...
  ```
* **EventHub 契约**：
  ```python
  class EventHub:
      def publish(self, topic: str, sender_id: str, data: dict) -> None: ...
      def subscribe(self, topic: str, subscriber_id: str, callback: Callable[[str, dict], None]) -> None: ...
      def unsubscribe(self, topic: str, subscriber_id: str) -> None: ...
  ```

### 2.3 量化验收标准 (Acceptance Criteria)
1. **AC-2.1**：Service Broker 注册未知服务或无权限调用时，必须在 5ms 内抛出结构化异常 `ERR-RPC-PERMISSION` 或 `ERR-SERVICE-NOT-FOUND`，且不得导致宿主进程崩溃。
2. **AC-2.2**：EventHub 异步事件广播延迟在 100 个并发订阅者场景下应保持在 $\le 2\text{ms}$，严禁消息队列溢出丢失。
3. **AC-2.3**：状态只读镜像读取延迟低于 50 微秒，且在微内核高频写入（44Hz）时无死锁、无脏读。

## 三、 方案三：插件的后期开发体系与二次开发支持

### 3.1 需求拆解与功能边界
* **CLI 脚手架（`tools/aima_plugin_cli.py`）**：提供一键生成插件模版、校验插件清单、本地打包分发的命令行工具。
* **离线 Mock 沙盒**：提供虚拟灯光宇宙、模拟音频节拍与时间轴输入的本地测试运行环境，供开发者在无真实硬件时进行端到端自测。
* **性能门禁探针**：在插件加载与运行期实时检测内存占用、CPU 耗时及 44Hz 帧率侵占情况，超标者自动熔断。

### 3.2 接口契约与签名
* **CLI 命令契约**：
  * `python tools/aima_plugin_cli.py create --type creative --name my_plugin`
  * `python tools/aima_plugin_cli.py validate --path plugins/my_plugin`
  * `python tools/aima_plugin_cli.py test-sandbox --path plugins/my_plugin --duration 10`
* **性能门禁探针指标阈值**：
  * 单帧渲染耗时：$\le 3.5\text{ms}$（44Hz 周期为 22.7ms，单插件硬预算占比 $< 15\%$）。
  * 内存泄漏指标：10 分钟压测内内存增量 $< 1\text{MB}$。

### 3.3 量化验收标准 (Acceptance Criteria)
1. **AC-3.1**：CLI 成功生成符合 `BaseCreativePlugin` 规范的脚手架目录，并通过 `verify_plugin_manifest.py` 静态校验。
2. **AC-3.2**：离线 Mock 沙盒可模拟 4 宇宙 2048 通道 DMX 输入，并正确可视化插件输出曲线。
3. **AC-3.3**：当插件单帧渲染耗时连续 5 次超过 $4.0\text{ms}$ 时，性能探针自动将其降级停用，并登记 `ERR-PLUGIN-PERF-VIOLATION`。

## 四、 方案四：整个系统的平滑升级演进方案

### 4.1 需求拆解与功能边界
* **平滑热重载与状态暂存迁移**：插件及系统升级时，通过 `on_save_state()` 导出运行时状态 JSON，卸载旧版本后由 `on_restore_state(state)` 无缝恢复。
* **Schema 迁移引擎（`core/migration_engine.py`）**：自动检测配置与状态数据的版本号（Schema Version），按序执行渐进式数据库/JSON 结构迁移脚本。
* **弃用垫片（Deprecation Shims）**：针对历史 API 与旧版配置字段提供过渡期兼容适配器，打印友好警告并不中断运行。

### 4.2 接口契约与签名
* **状态持久化接口**：
  ```python
  class LifecycleProtocol:
      def on_save_state(self) -> dict: ...
      def on_restore_state(self, state: dict) -> None: ...
  ```
* **Schema 迁移引擎契约**：
  ```python
  class MigrationEngine:
      def register_migration(self, from_version: str, to_version: str, migrator: Callable[[dict], dict]) -> None: ...
      def migrate_data(self, data: dict, target_version: str) -> dict: ...
  ```

### 4.3 量化验收标准 (Acceptance Criteria)
1. **AC-4.1**：插件在热重载过程中（Save $\to$ Unload $\to$ Reload $\to$ Restore），内部关键计数器与灯光模式保持零丢失。
2. **AC-4.2**：Schema 迁移引擎能够将 v5.0 旧版配置自动升级至 v5.3 结构，转换准确率达 $100\%$ 且无异常抛出。
3. **AC-4.3**：弃用垫片对所有历史遗留接口访问输出规范的 `DeprecationWarning` 日志，且保持调用链路完全畅通。

## 五、 给小代的实施建议（Implementation Guide for Xiao-Dai）

1. **模块化与边界隔离**：
   * 严禁在插件直接调用底层 `ctypes` 或操作系统内核文件，所有插件间通信必须通过 `ServiceBroker` 与 `EventHub`。
   * 开发 `core/migration_engine.py` 技术模块时，采用纯函数转换设计，确保单元测试覆盖率 $\ge 95\%$。
2. **测试与自测先行**：
   * 严格按照 `tests/` 下既有测试框架规范编写配套的单元测试与对抗性自测脚本。
   * 编码完成后必须确保本地回归套件全绿，方可提请小申进行架构审计。

## 六、 给小申的架构审计准入标准（Audit Gate for Xiao-Shen）

1. **架构合规性**：检查是否引入了非法跨层引用、违反三类插件依赖金字塔。
2. **异常与容错**：RPC 调用、状态序列化、Schema 迁移必须具备完整的异常捕获与故障码登记。
3. **性能与门禁**：验证探针机制是否对热重载和实时渲染线程造成锁竞争。
